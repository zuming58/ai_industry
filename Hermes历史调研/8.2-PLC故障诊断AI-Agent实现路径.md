# PLC 故障诊断 · AI Agent 实现路径

> **核心结论**：PLC 故障诊断**完全可以用 AI Agent 做**，但**关键不在"读 Modbus"**，而在**"证据门 + 状态机"**。这是老王您必须搞懂的核心架构。

---

## 一、PLC 故障诊断的两层分离

### 您的疑问完美命中关键

> "这个能不能进行一些错误的分析？我不知道 PLC 常见的报错会有什么东西，可能连了很多。"

> "比方说是 PLC 本身程序错误，它是能分析，还是说它如果说是连接哦，它连接的伺服的话，它伺服驱动器报错，PLC 能知道吗？"

### 故障的 4 大来源

| 来源 | 表现 | PLC 能否感知 |
|------|------|-------------|
| **PLC 本身程序错误** | 编译报错、运行时异常、FB 调用失败 | ✅ PLC 自身有诊断缓冲区 |
| **PLC 硬件故障** | 模块掉线、I/O 短路、电源异常 | ✅ PLC 自诊断（SF 灯）|
| **伺服/变频器报警** | 过流、过载、编码器异常、通讯中断 | ✅ PLC 通过通讯读取（Profinet/EtherCAT）|
| **传感器故障** | 信号卡死、漂移、抖动 | ⚠️ PLC 只能感知信号，需 AI 识别 |

**关键认知**：PLC 能感知**几乎所有**故障（通过诊断缓冲区 + 通讯），但**识别"是什么故障"和"如何修"**是 AI 的活。

## 二、AI 诊断 PLC 故障的标准方法

### Claude Code 读 Modbus 不能直接判故障的原因（Alex Hu 23文章 · 2赞）

> "一台 IVD 仪器上电后开始灌注试剂管路。气泡检测模块先返回 `air`，随后变为 `liquid`，设备正常进入待机。几小时后，同一个模块在吸液阶段再次返回 `air`。这两个信号看起来完全一样，工程含义却可能相反。"

**核心观点**：AI Agent 把"信号"误认为"故障"是常见错误。正确做法是**三层分离**：

```
┌─────────────────────────────────────┐
│  物理检测层：透明管内气体/液体/液滴   │  ← 传感器原始信号
├─────────────────────────────────────┤
│  通信层：TTL/UART/Modbus 数据有效性  │  ← 协议层校验
├─────────────────────────────────────┤
│  设备策略层：当前流程是否允许异常    │  ← 业务逻辑判断
└─────────────────────────────────────┘
```

> **AI 容易把三层压成一句"检测到气泡 = 管路故障"。但 Modbus 一次成功响应只能证明协议通畅，不能证明液体移动了。**

### "证据包"模型（正确做法）

```json
{
  "sample_time_ms": 19284321,
  "sequence": 1842,
  "fluid_state": "air",
  "communication_ok": true,
  "frame_valid": true,
  "sensor_ready": true,
  "config_revision": "tube-3.2-v2",
  "expected_config_revision": "tube-3.2-v2",
  "phase": "aspiration",
  "phase_elapsed_ms": 860,
  "event_duration_ms": 140,
  "pump_running": true,
  "pump_direction": "forward",
  "valve_route": "reagent_a_to_probe",
  "tube_setup_verified": true,
  "residue_suspected": false
}
```

**关键**：把**协议层有效数据**作为"证据"，**证据门**先证明数据可用，**确定性状态机**形成可测试的工程状态。

## 三、AI 诊断 PLC 故障的 4 大成熟方案

### 方案 1：诊断缓冲区解析（最基础）

**原理**：PLC 自带诊断缓冲区，可导出为日志

```
西门子 S7 诊断缓冲区导出格式：
"2026-08-26 10:23:15, I/O 错误, 模块 4 (DI 16x24VDC), 通道 7, 短路"

AI 处理：
1. 读取诊断日志
2. 解析错误代码
3. 匹配知识库（手册 + 历史故障库）
5. 输出诊断建议
```

**老王可做的产品**：诊断日志智能解析工具

### 方案 2：报警代码知识库 RAG（最实用）

**原理**：用历史故障 + 厂家手册构建 RAG

```
知识库：
- 西门子 S7 报警代码手册（2000+ 条）
- 汇川伺服报警代码（E.001-E.999）
- 三菱 FX 报警代码
- 客户历史故障库（500+ 条）
- 老师傅维修经验（PDF + 笔记）

RAG 检索：
用户问："伺服报警 E630.0 怎么修？"
1. 检索 → 找到手册 + 历史故障
2. 生成回答：
   "右伺服电机，Y轴，报警 E630.0（过载）。
   诊断结果：过去 30 分钟内，负载率从 65% 缓慢爬升至 112%，
   电流波形无明显冲击，振动频谱正常。
   综合判断：机械阻力增大，可能原因为导轨润滑不良。
   建议：
   1. 检查 Y 轴导轨润滑状态
   2. 临时将加速度从 0.8g 降至 0.6g"
```

**来源**：彭志强 63KB 白皮书 · AIPLC 异构融合架构

### 方案 3：状态机 + 多智能体协同（最专业）

**来源**：无敌金霸王 7 赞文章 · Copilot 多智能体测试

**核心思路**：用状态机思维做故障诊断

```
plc-functional-verifier 智能体：
- 状态机：自动 / 手动 / 急停 / 复位
- 顺控联锁：Permissives + Inhibits
- 硬件边界：传感器抖动、HSC 溢出、掉电恢复

该智能体是【只读分析模式】：
- 不下载程序
- 不 force IO
- 不触发硬件动作

```

## 四、AI 诊断 PLC 故障的工程化挑战

### 挑战 1：诊断缓冲区的"原始数据"问题

西门子诊断缓冲区记录的是**德语/英语**，工程师难以快速理解。

**AI 解决方案**：
```
原始日志：
"Event 1234: Distributed I/O: Station failure, Interface module IM 155-6 PN, Slot 1, Port 1"

AI 翻译 + 解释：
"事件 1234：分布式 I/O 站点故障
影响模块：IM 155-6 PN 接口模块（1 号槽）
端口：1
可能原因：
1. Profinet 网线松动
2. 接口模块电源异常
3. 远站 IO 模块掉线

紧急程度：⚠️ 高
建议处置：
1. 检查 1 号接口模块的网线
2. 检查模块 POWER 灯状态
3. 在 TIA Portal 中诊断 → 可访问性"
```

### 挑战 2：伺服报警的"业务语义"

**关键问题**：伺服报"过载"，是负载大、电机退磁、参数错、还是机械卡滞？

**AI 解决方案**：
```
1. 采集多模态数据：
   - 电流波形
   - 温度曲线
   - 振动频谱
   - 负载率趋势

2. 多维度关联分析：
   - 机械卡滞：电流波形有周期性尖峰
   - 电机退磁：反电动势常数下降
   - 参数错：负载率变化与正常工况差异明显

3. 输出诊断结论 + 推荐处置
```

### 挑战 3：老师傅经验数字化

**彭志强白皮书原话**：
> "AI 核实时采集伺服电机的多模态数据——电流波形、温度曲线、振动频谱、负载率变化趋势。**不是只盯着一个阈值，而是看全局、看趋势、看关联**。当检测到异常时，AI 自动进行根因分析。"

**落地方法**：
- 让老师傅口述典型故障的处理过程
- 转化为"if-then"规则库
- 喂给 AI 模型做 RAG 检索

## 五、AI Agent 诊断 PLC 故障的 5 步流程

### Step 1：数据采集

```
采集来源：
- PLC 诊断缓冲区（主动读取）
- 伺服报警寄存器（Profinet/EtherCAT 周期读）
- 传感器原始信号（高速采集）
- 操作记录（HMI/SCADA 日志）
```

### Step 2：证据门校验

```
对每条数据做有效性检查：
1. 通信成功？
2. 时间戳新鲜？
3. 序列号连续？
4. 传感器自检通过？
5. 配置版本一致？
```

> **关键**：**不在证据门失败的信号上做诊断**（参考 Alex Hu 23 文章）

### Step 3：状态机建模

```
当前设备处于哪个状态？
- 正常运行
- 工艺切换
- 故障报警
- 维护模式
- 急停

每个状态对应的"正常"信号是什么？
```

### Step 4：多智能体协同

```
智能体分工：
- 通信层 Agent：检查 Modbus/Profinet 数据
- 物理层 Agent：分析传感器原始信号
- 业务层 Agent：判断工艺流程是否正常
- 决策层 Agent：综合判断 + 输出建议

输出：诊断报告 + 推荐处置 + 风险等级
```

### Step 5：人工闭环

```
AI 输出：
"诊断：高概率（85%）为导轨润滑不足
建议：检查润滑 / 加注润滑脂
风险：低
可执行操作：[立即停机] [延迟处理] [忽略]"

操作员确认后：
- 自动写入维护日志
- 自动调整参数
- 自动推送通知给工程师
```
