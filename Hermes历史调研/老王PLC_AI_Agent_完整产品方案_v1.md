# 🎯 老王 PLC AI Agent 产品 · 三大方向完整方案

> **> 产品 愿景**：打造一个一个"工业 PLC AI 助手"工具——三个方向集成到一个 Agent 里：
>
> 1. **方向 A**：AI 盒子（边缘数据分析 + 故障诊断 Agent）
> 2. **方向 B**：AI 写程序（自然 → PLC 代码 + 编译验证）
> 3. **方向 C**：AI 调试 AutoShop（合伙人电气工程师用的 IDE 增强）
>
> **目标**：交给 Codex 开发，老王 + 合伙人 两个人就能用起来。

## 二、方向 A · AI 盒子（边缘数据分析 + 故障诊断）

### 2.1 目标

让老王能做出一个硬件小盒子：
- 插到 PLC 旁边 → 自动采集数据
- 数据不出厂（私有化）
- AI 自动分析 + 故障诊断
- 微信/钉钉推送报警

### 2.2 技术栈（Codex 需要开发的模块）

#### 模块 A1：硬件抽象层

```yaml
硬件选择:
  推荐: Jetson Orin NX 16GB（国产方案用 RK3588）
  接口:
    - 4×RJ45（PLC/MES/上位机/调试）
    - 2×USB 3.0
    - 1×RS485（Modbus RTU 备用）
    - 1×HDMI（本地显示）
  
  电源: 24V DC 工业宽压
  散热: 无风扇被动散热
  防护: 工业铝合金，宽温 -20~70°C
  
  来源（采购）:
    - 主力: Jetson Orin NX 16GB（¥15,000）
    - 国产备选: 赋创 FR50（¥20,000-30,000）
```

#### 模块 A2：协议采集层

```yaml
框架选择:
  核心: EMQX Neuron（已开源，ARM64 原生支持）
  
协议支持（按优先级）:
  P0 主协议:
    - Modbus TCP/RTU（汇川/三菱/西门子都支持）
    - OPC UA（西门子主推）
    - S7 协议（西门子专有）
    - Profinet/EtherCAT（西门子/倍福）
    
  P1 辅助协议:
    - DL/T645（电表）
    - IEC104（电力）
    - MQTT（IoT 设备）
    - HTTP API（向上接入 MES）
    
  开发工作量: 协议适配器已由 Neuron 提供，配置即可
```

#### 模块 A3：数据存储层

```yaml
时序数据: TDengine 3.0+
  性能: 单机 100万 点/秒
  压缩: 10-20x
  集成: 与 Neuron 直接对接
  
关系数据: PostgreSQL 16
  用途: 设备元数据、报警代码库、用户配置
  
缓存: Redis（可选）
  用途: 实时数据缓存 + 会话管理
  
数据保留策略:
  原始: 30 天
  聚合: 1 年
  知识库: 永久
```

#### 模块 A4：AI 推理层

```yaml
模型部署:
  框架: Ollama（一行命令启动）
  
模型选择（按场景）:
  轻量推理: DeepSeek-R1-Distill-Qwen-1.5B（INT4，~1GB）
  通用推理: DeepSeek-R1-Distill-Qwen-7B（INT4，~5GB）
  复杂推理: DeepSeek-R1-Distill-Qwen-14B（INT4，~10GB）
  
推理框架:
  简单任务: Ollama API
  高并发: vLLM
  
向量库: Chroma（小规模）→ Milvus（生产）
Embedding: BGE-large-zh-v1.5（中文最优）
```

#### 模块 A5：故障诊断 Agent

```yaml
诊断 Agent 架构（关键！）：
  输入层: 多源证据包
    - PLC 诊断缓冲区（西门子/汇川/三菱）
    - 伺服报警寄存器（Profinet/EtherCAT 通讯读取）
    - 传感器原始信号（振动/温度/电流）
    - HMI/SCADA 操作记录
    
  证据门（关键！不是信号就是故障）:
    - 通信有效？
    - 时间戳新鲜？
    - 序列号连续？
    - 传感器自检？
    - 配置版本一致？
    
  状态机: 当前工艺阶段 + 预期信号
  
  推理层: 多智能体协同
    - 通信层 Agent
    - 物理层 Agent
    - 业务层 Agent
    - 决策层 Agent
    
  输出: 故障代码 + 原因 + 药方 + 风险等级 + 处置建议
```

#### 模块 A6：知识库 RAG

```yaml
框架: FastMe RAG（制造业专属）
  
知识库内容:
  - 汇川报警代码手册（E.001-E.999）
  - 西门子诊断缓冲区说明
  - 三菱报警代码
  - 老师傅维修经验 PDF
  - 客户历史故障库
  
文档拆解器（FastMe 内置）:
  - log: 故障日志、运行日志
  - manual: 操作手册、维修手册
  - business: 工单、质检单
  - sop: 作业指导书、BOM、工艺流程
  
场景路由:
  - fault_diagnosis: 故障诊断
  - manual_query: 手册查询
  - work_order_trace: 工单追溯
  - default: 默认问答
```

#### 模块 A7：推送与告警

```yaml
推送通道:
  微信: 企业微信机器人 webhook（推荐）
  钉钉: 钉钉机器人 webhook
  飞书: 飞书机器人 webhook
  SMS: 阿里云短信 / 腾讯云短信（备用）
  
告警等级:
  P0: 紧急停机 → 立即推送 + 电话
  P1: 严重故障 → 立即推送
  P2: 一般异常 → 5 分钟内推送
  P3: 提示信息 → 汇总日报
```

## 三、方向 B · AI 写程序（自然语言 → PLC 代码）

### 3.1 目标

老王想做的是：
- 自然语言描述设备工艺 → AI 生成 PLC 代码
- 代码可以直接导入 AutoShop（汇川）/ TIA Portal（西门子）/ CODESYS
- AI 生成的代码自动编译检查 → 通过率 > 80%
- 老王 + 合伙人用得上

### 3.2 技术栈（Codex 需要开发的模块）

#### 模块 B1：自然语言理解层

```yaml
输入:
  - 自然语言工艺描述
  - 流程图（PNG/JPG/PDF）
  - I/O 分配表（CSV/Excel）
  - 设备清单（文本/表格）
  - 历史程序（梯形图/ST 代码参考）

LLM 选择:
  推荐: DeepSeek-V3 / Qwen2.5-72B（代码能力强）
  备选: GPT-4o / Claude 3.5（如果预算充足）

提示词工程:
  - 角色: 你是 PLC 编程专家
  - 上下文: PLC 型号 + 工艺要求 + 编程规范
  - 输出格式: ST/SCL/梯形图代码 + 注释
  - 约束: 符合 IEC 61131-3 / 西门子 SCL 规范
```

#### 模块 B2：代码生成层

```yaml
支持编程语言（按优先级）:
  P0（汇川，老王主要客户）:
    - AutoShop ST 语言
    - AutoShop 梯形图（LD）
    - AutoShop SFC（顺序功能图）
    
  P1（西门子，复旦/西门子客户）:
    - TIA Portal SCL
    - TIA Portal LAD（梯形图）
    - TIA Portal FBD
    
  P2（CODESYS，国产部分品牌）:
    - CODESYS ST
    - CODESYS CFC

代码模板库:
  框架: FastMe RAG（复用）
  内容:
    - 常见工艺模板（气缸控制、伺服控制、PID）
    - 标准库函数（汇川/西门子/三菱）
    - I/O 分配示例
    - 历史优秀程序
```

#### 模块 B3：编译验证层（关键！）

```yaml
汇川 AutoShop 集成:
  API: AutoShop 提供 COM 接口（待调研）
  方式:
    1. AI 生成 ST 代码 → 保存为 .st 文件
    2. 调用 AutoShop 命令行编译
    3. 解析编译错误 → 反馈给 AI
    4. AI 修复 → 重新编译 → 循环
  
  关键工具: AutoShop CLI / 脚本接口（Codex需研究）
  
西门子 TIA Portal 集成:
  API: TIA Openness（已开放，需授权）
  参考: RealPLC TIA Agent 已实现完整闭环
  
  关键工具: TIA Openness API（C#） + Python 包装

CODESYS 集成:
  API: CODESYS Scripting Engine
  参考: RealPLC CODESYS 已集成（无需费用）
  
  关键工具: CODESYS IDE 脚本 + Python 包装
```

#### 模块 B4：质量检查层

```yaml
代码审查 Agent（plc-functional-verifier）:
  来源: GitHub Copilot 多智能体测试
  
  工具: 只读分析模式
  检查项:
    - 状态机切换边界
    - 顺控联锁 Permissives/Inhibits
    - HSC 计数器边界
    - 掉电恢复逻辑
    - NVRAM 数据完整性
    - 安全互锁
    - 急停逻辑
  
  输出: 审查报告 + 风险点 + 修复建议
```

#### 模块 B5：双向转换层

```yaml
ST ↔ 梯形图 互转:
  参考: 汇川已实现一键互转
  
  应用:
    - 老客户老程序（梯形图）→ AI 学习转 ST
    - AI 生成 ST → 工程师查看梯形图
    - 国产/进口 PLC 程序迁移
```

### 3.3 工作流

```
输入：自然语言工艺需求
   ↓
模块 B1：解析（LLM）
   ↓
模块 B2：生成代码（LLM + 模板库）
   ↓
保存为 .st 文件
   ↓
模块 B3：调用 AutoShop 编译
   ↓
   ├── 编译通过 → 模块 B4：质量审查
   │                ↓
   │              输出代码包
   │
   └── 编译失败 → AI 修复 → 重新编译
                  ↓
                  最多 3 轮循环
                  ↓
                  还失败 → 人工介入
```

### 3.5 Codex 开发建议

```

  P0: 汇川 AutoShop ST 代码生成 + 编译验证
  P1: 西门子 TIA SCL 代码生成 + 编译验证（参考 RealPLC）
```

## 四、方向 C · AI 调试 AutoShop（合伙人电气工程师用）

### 4.1 目标

让老王的合伙人（电气工程师）能用得上：
- 在 AutoShop IDE 里调用 AI 助手
- AI 帮看代码、找 bug、优化
- 自然语言对话调试 PLC 程序
- 自动测试和验证

### 4.2 技术栈

#### 模块 C1：IDE 集成

```yaml
AutoShop（汇川）集成:
  方式 1（推荐）: LSP 协议（Language Server Protocol）
    - 汇川 AutoShop 可能支持 LSP
    - 老王合伙人可以验证
    
  方式 2: AutoShop 插件 SDK
    - 汇川可能有 COM/.NET 插件接口
    - 需要 Codex 调研
    
  方式 3: 独立 Web IDE
    - 我们的 Web 应用 + AutoShop 联动
    - 类似 VS Code + Continue
    
  备选 IDE 集成:
  TIA Portal: TIA Openness API（RealPLC 已实现）
  CODESYS: Scripting Engine（RealPLC 已实现）
```

#### 模块 C2：代码辅助层

```yaml
代码补全:
  - 基于上下文的代码补全
  - 基于历史项目风格的补全
  - 库函数自动提示

代码审查:
  - plc-functional-verifier 智能体（参考无敌金金霸王）
  - 静默运行，不打断工程师

代码解释:
  - 选中代码 → AI 解释
  - 自然语言问答："这段代码什么意思？"
  - 中文友好
```

#### 模块 C3：调试助手

```yaml
在线调试:
  - PLC 实时状态查询
  - 变量值监控
  - 报警历史查看
  
离线调试:
  - 仿真运行（PLCSIM 类似）
  - 单步执行
  - 断点管理
  
知识库问答:
  - "FX-5U 的 HSC 怎么用？"
  - "Modbus 通讯失败怎么排查？"
  - "PID 参数怎么调？"
```

#### 模块 C4：测试自动化

```yaml
单元测试:
  - 自动生成测试用例
  - 验证边界条件
  - 覆盖率报告

集成测试:
  - 多 PLC 协同测试
  - 通讯协议测试
  - 报警流程测试
```

## 一、AI 为什么能写 PLC 程序（原理）

### 老王的判断完全正确

> "PLC 它本来也是一种编程语言，它有梯形图，也有那种像代码一样编程的，它其实你编完以后，它可以转成这个梯形图。"

**PLC 编程语言的本质**：

| 语言 | 标准 | 性质 |
|------|------|------|
| **梯形图（LD）** | IEC 61131-3 | 图形化（电气符号） |
| **结构化文本（ST）** | IEC 61131-3 | 文本（类似 Pascal） |
| **SCL（西门子）** | 西门子专有 | ST 的超集 |
| **指令表（IL）** | IEC 61131-3 | 汇编式（已淘汰） |
| **功能块图（FBD）** | IEC 61131-3 | 图形化 |
| **顺序功能图（SFC）** | IEC 61131-3 | 状态机 |

✅ **ST/SCL 是纯文本代码**，与 Python、C++ 无异 → **AI 直接生成文本代码**
✅ **梯形图也是文本表示**（XML 格式），AI 可以生成文本，再转换为图形

> **关键洞察**：所有 PLC 编程语言底层都是文本。AI 写代码 = LLM 生成文本。

## 四、AI 写 PLC 程序的"前提条件"

> 老王您问的"事先要输入哪些条件"——这是关键！

### 输入条件清单（最少必要信息）

#### 1. 硬件配置（必须）

```
- PLC 品牌型号：西门子 S7-1200 / 三菱 FX5U / 汇川 H5U
- 模块清单：CPU + DI/DO/AI/AO 模块型号
- 伺服/变频器：品牌型号 + 通讯协议
- 传感器：光电/接近/限位/编码器 类型与位置
- HMI：型号与界面需求
```

#### 2. I/O 分配表（必须）

```
输入点：
- X0: 启动按钮（常开）
- X1: 停止按钮（常闭）
- X2: 左限位开关
- X3: 右限位开关

输出点：
- Y0: 气缸1 电磁阀
- Y1: 气缸2 电磁阀
- Y2: 伺服使能
```

#### 3. 控制逻辑（必须 · 核心）

```
工艺流程：
1. 按启动 → 进入自动模式
2. 气缸1 伸出 → 检测左限位 → 气缸2 伸出
3. 气缸2 检测下限位 → 气缸2 缩回
4. 气缸2 检测上限位 → 气缸1 缩回
5. 气缸1 检测右限位 → 回到步骤 2（自动循环）

异常处理：
- 任一超时（3 秒）→ 报警 + 停机
- 急停按钮 → 全部停止 + 复位
```

#### 4. 工艺参数（推荐）

```
- 延时参数：气缸动作间隔 500ms
- 安全参数：急停响应 < 100ms
- 报警阈值：压力 < 0.4MPa 报警
- 通讯参数：从站地址 1，波特率 19200
```

#### 5. 编程规范（强烈推荐）

```
- 命名规范：g_bMotor_Start（全局布尔-电机-启动）
- 程序结构：主程序 OB1 + FB100（气缸控制）+ DB100（数据块）
- 注释要求：每个 FB 必须有头部说明 + 关键变量注释
```

## 五、关键技术坑（避免踩雷）

### 坑 1：AI 生成的代码"看起来对，编译报错"

**原因**：AI 不了解 TIA Portal 特定版本 API、不了解项目级变量
**对策**：用 TIA Openness API 自动导入并编译验证（RealPLC 路线）

### 坑 2：AI 不懂现场工艺约束

**原因**：AI 只有通用知识，没有"气缸密封圈老化"等现场经验
**对策**：
- 提供典型工艺库（俊杰工控 304 篇专栏）
- 提供历史故障库
- 用 RAG 检索厂内知识库

### 坑 3：梯形图 vs ST 代码的转换问题

**原因**：复杂梯形图转 ST 代码可能丢失语义
**对策**：
- 优先用 ST/SCL 直接生成（避免转换损失）
- 汇川的"一键互转"已成熟（梯形图 ↔ ST）
- 简单梯形图才适合互转

### 坑 4：AI 在控制回路中的安全性

**问题**：AI 不能直接进控制回路（实时性 + 安全性）
**方案**（AIPLC 白皮书）：
```
实时核：微秒级运动控制（确定性硬实时）
AI 核：轻量化大模型（3-6 TOPS）
两者通过共享内存通信，AI 只能"建议"，不能"强控"
关键安全功能（急停/安全限位）由实时核独立掌控
```

> **核心结论**：PLC 故障诊断**完全可以用 AI Agent 做**，但**关键不在"读 Modbus"**，而在**"证据门 + 状态机"**。这是老王您必须搞懂的核心架构。

## 一、PLC 故障诊断的两层分离

### 您的疑问完美命中关键

> "这个能不能进行一些错误的分析？我不知道 PLC 常见的报错会有什么东西，可能连了很多。"

> "比方说是 PLC 本身程序错误，它是能分析，还是说它如果说是连接哦，它连接的伺服的话，它伺服驱动器报错，PLC 能知道吗？"

### 故障的 4 大来源

| 来源 | 表现 | PLC 能否感知 |
|------|------|-------------|
| **PLC 本身程序错误** | 编译报错、运行时异常、FB 调用失败 | ✅ PLC 自身有诊断缓冲区 |
| **PLC 硬件故障** | 模块掉线、I/O 短路、电源异常 | ✅ PLC 自诊断（SF 灯）|
| **伺服/变频器报警** | 过流、过载、编码器异常、通讯中断 | ✅ PLC 通过通讯读取（Profinet/EtherCAT）|
| **传感器故障** | 信号卡死、漂移、抖动 | ⚠️ PLC 只能感知信号，需 AI 识别 |

**关键认知**：PLC 能感知**几乎所有**故障（通过诊断缓冲区 + 通讯），但**识别"是什么故障"和"如何修"**是 AI 的活。

## 二、AI 诊断 PLC 故障的标准方法

### Claude Code 读 Modbus 不能直接判故障的原因（Alex Hu 23文章 · 2赞）

> "一台 IVD 仪器上电后开始灌注试剂管路。气泡检测模块先返回 `air`，随后变为 `liquid`，设备正常进入待机。几小时后，同一个模块在吸液阶段再次返回 `air`。这两个信号看起来完全一样，工程含义却可能相反。"

**核心观点**：AI Agent 把"信号"误认为"故障"是常见错误。正确做法是**三层分离**：

```
┌─────────────────────────────────────┐
│  物理检测层：透明管内气体/液体/液滴   │  ← 传感器原始信号
├─────────────────────────────────────┤
│  通信层：TTL/UART/Modbus 数据有效性  │  ← 协议层校验
├─────────────────────────────────────┤
│  设备策略层：当前流程是否允许异常    │  ← 业务逻辑判断
└─────────────────────────────────────┘
```

> **AI 容易把三层压成一句"检测到气泡 = 管路故障"。但 Modbus 一次成功响应只能证明协议通畅，不能证明液体移动了。**

### "证据包"模型（正确做法）

```json
{
  "sample_time_ms": 19284321,
  "sequence": 1842,
  "fluid_state": "air",
  "communication_ok": true,
  "frame_valid": true,
  "sensor_ready": true,
  "config_revision": "tube-3.2-v2",
  "expected_config_revision": "tube-3.2-v2",
  "phase": "aspiration",
  "phase_elapsed_ms": 860,
  "event_duration_ms": 140,
  "pump_running": true,
  "pump_direction": "forward",
  "valve_route": "reagent_a_to_probe",
  "tube_setup_verified": true,
  "residue_suspected": false
}
```

**关键**：把**协议层有效数据**作为"证据"，**证据门**先证明数据可用，**确定性状态机**形成可测试的工程状态。

## 六、AI BOX 与 PLC 的连接方式

### 方式 1：Profinet 镜像（推荐 · 无侵入）

```
客户网络（生产）：
[PLC] ←Profinet→ [远程 I/O]

AI BOX 通过镜像端口监听：
[AI BOX] ←Profinet Mirror→ [Switch 镜像口]

✅ 优点：
- 零侵入，PLC 程序不变
- 不影响实时性
- 主流 PLC 都支持

⚠️ 限制：
- 需要交换机支持镜像
- 部分老 PLC 不支持
```

### 方式 2：Modbus TCP 主动读（最简单）

```
[AI BOX] --Modbus TCP 读寄存器--> [PLC]

✅ 优点：
- 配置简单
- 几乎所有 PLC 都支持
- 老 PLC 也能用

⚠️ 限制：
- 数据延迟（取决于扫描周期）
- 数据维度有限
```

### 方式 3：OPC UA 订阅（最先进）

```
[AI BOX] --OPC UA 订阅--> [PLC OPC UA Server]

✅ 优点：
- 数据语义丰富
- 实时性好
- 支持历史数据

⚠️ 限制：
- 需 PLC 支持 OPC UA
- 配置稍复杂
```

### 方式 4：西门子 S7 协议（西门子专有）

```
[AI BOX] --S7 Communication--> [S7-1200/1500]

✅ 优点：
- 直接读取西门子 DB 块
- 高效
- 不需要额外授权

⚠️ 限制：
- 仅限西门子 PLC
```

## 七、AI BOX 的 7 大场景应用

### 场景 1：实时故障诊断

```
触发：PLC 报警
AI BOX：
1. 读取诊断缓冲区
2. 读取伺服报警代码
3. 查询本地 RAG 知识库
4. 输出诊断结论 + 推荐处置
5. 推送微信/钉钉

时效：< 3 秒
```

### 场景 2：老师傅知识数字化

```
第一次部署：
1. 老师傅口述典型故障处理过程
2. AI 转化为结构化规则库
3. 存入本地知识库

后续运行：
1. 设备出现类似故障
2. AI 自动匹配历史经验
3. 输出处理建议
```

### 场景 3：预测性维护

```
数据采集：
- 振动（加速度传感器）
- 温度（热电偶）
- 电流（互感器）

AI 模型：
- LSTM 时序预测
- 异常检测

输出：
- "主轴 7 天内可能故障，建议检修"
```

### 场景 4：参数自适应调整

```
场景：客户换了批物料（电芯厚度变了 0.3mm）
AI BOX：
1. 检测到异常参数
2. 推理新参数
3. 输出建议（不直接修改 PLC）
4. 工程师确认后写入
```

### 场景 5：自然语言查询设备状态

```
客户问："5 号车床今天效率怎么样？"

AI BOX：
1. 查询设备数据
2. 检索知识库
3. 生成回答

输出：
"5 号车床今日运行 8 小时，加工 320 件，
OEE 85%，比昨日提升 5%。
无报警。设备状态良好。"
```

### 场景 6：自动化工单

```
场景：设备出现故障
AI BOX：
1. 识别故障类型
2. 自动创建维护工单
3. 推送维修人员
4. 维修完成后自动更新知识库
```

### 场景 7：远程运维

```
客户在苏州，工程师在上海
AI BOX：

2. AI 自动诊断
```
