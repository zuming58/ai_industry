# Historical Research Review

## 1. 总体判断

WorkBuddy 与 Hermes 的历史调研都抓住了正确方向：PLC 比机械三维自动建模更适合先形成 AI 工程闭环；输入必须结构化；LLM 不应独占控制逻辑；程序必须经过编译、仿真与人工审批；诊断需要状态机、时序证据和手册知识库。

两套材料最大的问题不是思路，而是把一些“可能存在的接口”写成了“已经可用的能力”。本项目将所有厂商工具接口按“已由官方证实、第三方实验性、尚未证实”分级，避免在错误前提上搭建完整产品。

## 2. 可直接继承的观点

- 以机电对接表、动作顺序和电气资料为输入，而不是要求用户只用自然语言描述整机；
- 先建立统一设备模型，再生成厂商程序；
- 让 LLM 负责解释、补全建议、歧义发现和受控修复，让模板、规则和编译器负责确定性；
- 静态检查、厂商编译、软件仿真、人工签核构成多层验证；
- 故障诊断采用证据门控和状态机，不把故障码检索包装成根因诊断；
- 边缘设备主要承担数据采集和缓冲，强推理可以留在企业内网工作站；
- 所有操作需要版本、差异、审批和审计日志。

## 3. 必须修正或降级为假设的观点

| 历史主张 | 本次结论 | 处理方式 |
|---|---|---|
| AutoShop 有稳定公开的 CLI、COM 或 LSP | 未找到汇川官方公开证据 | 作为技术验证项，不进入核心架构承诺 |
| InoProShop 可用 PLCopen XML 完整导入工程 | PLCopen XML 是交换标准，但厂商扩展和导入语义决定实际可用范围；未找到汇川官方完整工程导入证明 | 只认本地实测结果 |
| 开源 EtherCAT 解析器接在网络口即可无侵入诊断 | EtherCAT 在线无侵入抓包通常需要专用 TAP/监测端口，且还要有 ESI/PDO 映射 | 第一版优先 PLC/OPC UA/Modbus 只读采集；被动总线监测后置 |
| 开源 Neuron 可免费覆盖 OPC UA、S7、EtherNet/IP 等工业协议 | 当前开源核心主要覆盖 Modbus/MQTT，多种协议属于商业 NeuronEX | 不设为 MVP 必选依赖 |
| 通用软 PLC 的测试可证明汇川/三菱程序可用 | 商业 PLC 的语义、扫描、运动控制库和厂商扩展并不完全相同 | 开源软 PLC 只做前置检查，厂商编译器/模拟器才是验收门 |
| ST 可以无损转换成任意厂商 LD | 图形语言、网络布局、扩展指令和工程元数据都影响转换 | 首版以 ST 和厂商功能块模板为主，不承诺通用 ST↔LD |
| 一个 7B 本地模型足以承担完整 PLC 工程 | 模型大小不能替代领域数据、检索、规则和验证，必须用真实任务集评测 | 模型可插拔，以任务通过率决定部署规格 |
| 四周可以完成生产级双引擎 MVP | 可在四周做演示，但无法同时完成厂商适配、仿真测试、诊断与安全治理 | 建议 12–16 周完成窄范围 MVP |
| 编译通过等于程序可用 | 编译只能证明语法/类型层面，无法证明工艺、异常恢复、节拍和安全 | 强制验收测试、时序断言、异常注入和人工评审 |

## 4. 新发现的关键机会

公开的 `AutoShopAgentInterface` 项目提供 H5U/AutoShop 工作区 JSON 导出与应用、ST 检查、工程配置和 UI 自动化编译等线索，说明汇川路线并非完全无路可走。但它规模小，包含预编译代理，源代码完整性、许可边界、软件版本兼容性和真实设备可靠性都需要审查。因此它适合作为适配器原型和验证加速器，不应未经审计就成为商业产品的底座。

三菱的优势是官方 GX Simulator3 与 MX Component 能构成较清晰的“模拟 PLC + 外部读写变量”测试路径。公开资料中仍未确认可靠的 GX Works3 自动代码导入 API，但即使保留人工导入，三菱也可能更早跑通可重复的闭环验收。

CODESYS 官方 MCP 已提供读取工程、修改 ST POU、编译和错误反馈能力，是行业趋势和架构标杆；但它要求特定版本和 Professional Developer Edition。社区 MCP 在版本支持、无头模式和安全行为上与官方产品不同，不能混为一谈。

## 5. 本项目如何吸收历史成果

- 不修改现有 `WorkBuddy历史调研` 与 `Hermes历史调研`，它们继续作为原始参考；
- 本目录把经过核实的结论固化为决策基线；
- 未核实的接口进入 `roadmap.md` 的技术验证清单；
- 所有新设计以 `MachineSpec`、厂商适配层、验证层和只读诊断层为主轴；
- 后续若本地实测推翻当前结论，更新证据台账和版本决策，不悄悄改写历史。
