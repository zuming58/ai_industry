# User Vision and Domain Context

## 1. 发起人的能力与位置

发起人是苏州地区的非标自动化机械设计工程师，有十几年到二十年的设备设计与交付经验，长期与电气工程师合伙完成整机设备。近期已学习 AI 视频、Web Coding 和 AI 硬件，希望形成两条相互增强的事业路径：

- 作为面向制造企业的 FDE/前端部署工程师，进入现场识别真实需求并完成落地；
- 把 AI 沉入自己的机械设计和 PLC 工程经验，而不是另做一个脱离行业的通用聊天产品。

机械侧已开始建设计算选型网页，涉及伺服、丝杆、同步带等，未来可能扩展招聘与工程师交流。长期希望接近自动出图，但认可现阶段 AI 直接稳定控制 SolidWorks 完成非标整机设计仍有较大困难。因此，本轮优先选择数据结构更清楚、可编译、可仿真的 PLC 工程与故障诊断。

## 2. 当前非标设备协作流程

机械工程师完成三维设计后，会向电气工程师交付“机电对接表”。典型内容包括：

- 用截图和箭头标出机构、伺服、气缸、传感器等；
- 按团队规则给予唯一代码，例如 Servo01、Cylinder02、对应的原点/极限/到位传感器；
- 描述设备动作顺序，例如托盘进站、举升定位、夹紧、加工、放行；
- 在每个步骤标出动作元件、确认传感器、互锁关系和预计耗时；
- 汇总节拍，验证机械动作的时间预算。

电气工程师据此选择 PLC、远程 I/O、伺服、变频器等，形成硬件 BOM 和电路图，再编写、仿真和现场调试 PLC 程序。大公司可能把硬件、软件和现场调试分开，小公司常由一名 PLC 工程师全程承担。电气工程师主要依赖机电对接表和口头讲解理解设备，只有复杂机构才频繁查看三维数模。

这里用户口述的“L 接口”按行业上下文更可能是 **I/O 接口表或点位表**。项目实施时应由用户和电气伙伴用一份真实资料确认术语，不能直接把语音转写当成最终字段名。

## 3. 希望实现的两个产品能力

### 3.1 PLC 程序工程

把现有机电对接表、动作顺序、节拍表、电气/I/O 资料变成受约束的结构化输入。Agent 逐步引导填写并主动发现缺项，随后：

1. 建立整台设备的执行元件、传感器、I/O、状态、动作、互锁、报警和参数模型；
2. 生成 PLC 程序、变量表、报警表、调试说明和验收测试；
3. 进入厂商工程软件编译；
4. 在软件 PLC 或厂商模拟器中驱动输入、观察输出、验证步骤与异常分支；
5. 把错误反馈给受控修复流程，最终由电气工程师审批和下载。

初期聚焦汇川和三菱，优先选择一条最能跑通“生成—编译—仿真—报告”的链路。

### 3.2 设备故障诊断

故障码只是证据之一。诊断能力需要综合：

- 当前设备模式、状态与动作步骤；
- PLC、伺服、变频器和远程 I/O 的报警码；
- 命令、反馈、传感器和通信质量的前后时序；
- 设备结构、工艺顺序、互锁和报警定义；
- 操作员用文字、语音、图片或视频描述的物理现象；
- 最近改过的程序、参数、机械件和电气接线；
- 对应版本的手册、图纸和已解决案例。

Agent 应给出“证据—候选原因—验证动作—风险—修复建议”，而不是仅输出一个看似确定的答案。程序修复只能生成离线差异，经编译、仿真、审批后由工程师实施。

## 4. 现场部署设想

工厂通常不允许生产数据直接进入公网模型。因此部署需要分层：

- 开发和演示阶段可使用云端模型，但只能处理脱敏或合成资料；
- 企业落地时，设备资料、日志、知识库和模型推理可以部署在企业内网工作站或服务器；
- 车间侧小盒负责协议接入、只读采集、缓冲、规则告警和加密传输，不承担所有大模型推理；
- 工作站不必拖到机台旁，可放在办公室、控制室或服务器间，通过受控 OT 网络访问采集网关；
- 调试笔记本可用于离线服务，但不是首版必须硬件。

小盒的核心壁垒不是“塞进一个大模型”，而是可靠、只读、安全的设备连接器，标准化证据包，以及与设备规格和工程版本的精确关联。

## 5. 产品长期形态

长期不是两个孤立工具，而是一个共享设备数字规格的工程平台：

- 设计阶段：机械、电气和控制共同建立设备规格；
- 开发阶段：生成代码、文档和测试；
- 调试阶段：记录修改、证据和验收结果；
- 运行阶段：诊断系统继续使用同一份设备拓扑、状态机、报警和参数；
- 复用阶段：已验证的机构模块、功能块、测试和故障案例进入企业资产库。

最有价值的行业资产将是“真实非标机构模式 + 可验证控制模板 + 失败与恢复案例”，而不是单独的提示词或某个大模型名称。
