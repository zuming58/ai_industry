# 08 技术方案：集成 Agent 架构与技术栈

> 2026-08-27 定稿。本文回答三个问题：
> 1. 能不能做一个统一 Agent，把 PLC 编程 + 故障诊断集成成一个工具去卖？
> 2. CODESYS IDE 能不能封装进自己的产品？（授权红线）
> 3. 完整技术栈是什么？（可直接交给 Codex 开发）

---

## 一、核心结论（先看这个）

**能做一个统一 Agent 工具去售卖，但不能把 CODESYS"打包进去"——走"调用式集成"，这是唯一合规且可行的路。**

### 1.1 三种做法的判定

| 做法 | 可行性 | 原因 |
|------|--------|------|
| ① 把 CODESYS 安装包打进自己的产品一起分发 | ❌ 不行 | 违反 CODESYS EULA。IDE 免费但只允许用户自己从官网下载安装，禁止第三方再分发 |
| ② 改 CODESYS 界面、贴自己的牌当自研产品 | ❌ 不行 | 同上，且技术上门槛极高（CODESYS 是闭源 C# 平台） |
| ③ **调用式集成**：用户电脑自己装免费 CODESYS，我们的 Agent 通过 MCP 协议/脚本引擎在后台驱动它 | ✅ 正确路线 | IDE 永久免费、可合法装在任意工作站；MCP Server 是 MIT 开源。我们的 UI 在前，CODESYS 在后当"编译引擎"，就像 Cursor 调用 gcc 一样 |

### 1.2 授权红线清单（2026-08 官方信息核实）

| 组件 | 费用 | 商用限制 | 对我们的影响 |
|------|------|----------|--------------|
| CODESYS Development System V3（IDE） | 免费 | 只能用户自行下载安装；不能再分发安装包 | 产品文档里写"首次使用请从 store.codesys.com 下载 IDE"，我们的安装器只装自己的部分 |
| CODESYS Control Win V3/Win SL（软PLC仿真） | 免费 demo 模式 | **每次启动 2 小时后自动停机**，需手动重启 | 对我们是好事：AI 验证测试单次跑几分钟，2小时限制完全够用。测试完自动重启即可 |
| 软PLC 正式授权（7×24 运行） | 收费（Application-Based，按 IO 点数/总线数分 8 档） | 单设备授权 | 只在"客户要长期跑仿真"场景才需要，MVP 阶段不碰 |
| codesys-mcp-toolkit 等开源 MCP Server | MIT 协议免费 | 保留版权声明即可商用 | 可以直接改、直接集成进自己的产品 |
| 汇川 InoProShop | 免费（汇川生态内） | 闭源，无对外脚本接口（待合伙人实测确认） | 走 PLCopen XML 导入路线，不走脚本引擎 |
| DeepSeek API 等大模型 | 按 token 付费 | 无限制 | 成本可控 |

**一句话：我们的产品 = 自研 Agent 外壳 + 知识库 + MCP 工具链，CODESYS 由用户自装、被我们调用。没有任何再分发风险。**

## 二、产品形态定义

**产品名（暂定）：非标产线 AI 助手（双引擎 Agent）**

一个 Windows 桌面应用，面向非标设备厂和小型集成商的电气工程师，一个界面三个引擎：

```
┌─────────────────────────────────────────────────┐
│              我们的 Agent 桌面应用                │
│  ┌───────────┐ ┌───────────┐ ┌───────────────┐  │
│  │ 引擎A      │ │ 引擎B      │ │ 引擎C(后续)    │  │
│  │ PLC编程    │ │ 故障诊断    │ │ 工艺/报价等    │  │
│  │ 助手       │ │ 医生       │ │ 扩展位        │  │
│  └───────────┘ └───────────┘ └───────────────┘  │
│           Agent 编排层（大脑，LangGraph）          │
│  ┌──────────────────────────────────────────┐   │
│  │ MCP 工具层 │ RAG 知识库 │ 任务队列 │ 用户库  │   │
│  └──────────────────────────────────────────┘   │
└───────────────────┬─────────────────────────────┘
                    │ MCP 协议（本地进程通信）
        ┌───────────┴────────────┐
        ▼                        ▼
  用户自装的 CODESYS IDE      边缘盒/现场PLC（诊断数据）
  （编译引擎 + 软PLC仿真）     （EtherCAT/OPC UA 采集）
```

**为什么三引擎合一而不是三个产品：** 共用同一个用户系统、同一个行业知识库（这是核心壁垒）、同一套 Agent 编排。编程和诊断在非标行业本来就是同一批人（电气工程师）的同一台机器。

## 三、技术方向 A：PLC 编程引擎（AI 写程序 + 自动验证）

### 3.1 完整数据流（这是产品的灵魂）

```
用户输入：工艺描述 + IO表（Excel/CSV）
    ↓
[1] 需求解析：LLM 把工艺描述结构化 → 动作序列、互锁条件、安全要求
    ↓
[2] IO 映射：把 IO 表绑定到程序变量（DI_xxx / DO_xxx / 轴号）
    ↓
[3] 代码生成：LLM 按"非标行业模板"生成 ST 代码（结构化文本）
    ↓
[4] 三关验证（参考 RealPLC 闭环 + 108-bug 研究教训）：
    ├─ 第一关：静态检查（语法/命名规范/未使用变量）
    ├─ 第二关：CODESYS 编译（调用用户 IDE，回读编译错误）
    └─ 第三关：软PLC 仿真测试（下载到 Win V3 软PLC，模拟 IO 翻转，
       验证关键行为：急停优先级、互锁逻辑、启动条件）
    ↓
[5] 错误回传修复：验证失败 → 错误信息喂回 LLM → 重新生成 → 循环（上限5次）
    ↓
[6] 输出：ST 源码 + PLCopen XML（给 InoProShop 导入）+ 生成报告
```

**第三关是核心竞争力**：调研里那个 108-bug 实验证明了"AND 改 OR 照样编译通过"——只有编译没有仿真验证的 AI 编程工具都是半成品。仿真测试用例从哪来？从第 [1] 步结构化的需求自动生成——需求说"急停按下时所有轴必须停止"，就自动生成"模拟急停信号=ON，断言所有轴状态=停"的测试。**需求和测试同源，这是别家没做的。**

### 3.2 技术组件

| 组件 | 选型 | 说明 |
|------|------|------|
| 大模型 | DeepSeek-V3（API），备用 Qwen | 生成 ST + 解析错误。走 OpenAI 兼容接口 |
| IDE 驱动 | codesys-mcp-toolkit（MIT，改造） | 通过 IronPython 脚本引擎操控 CODESYS：建 POU、写入 ST、编译、读错误、下载软PLC、读写变量 |
| 软PLC | CODESYS Control Win V3（用户随 IDE 装，免费） | 2小时 demo 限制对分钟级测试无影响 |
| 静态检查 | 自研规则引擎（正则+AST） | 行业规范：命名、注释、双线圈检测 |
| 模板库 | 自研，非标行业积累 | 站位循环、安全回路、伺服使能/点动/回零、机器人交互握手——这就是壁垒 |
| 测试框架 | 自研 TestSpec 生成器 | 从结构化需求自动生成仿真测试用例 |

### 3.3 你需要懂的最小知识（老王补课区）

- **ST 语言**：类似 Pascal 的文本 PLC 语言，AI 写它最准。梯形图是从 ST 反向转换的（CODESYS 支持互转）
- **软PLC**：装在 Windows 上的软件模拟 PLC，不用买硬件就能让程序真实跑起来
- **PLCopen XML**：IEC 标准的工程交换格式，InoProShop 能导入，这就是绕过汇川封闭接口的桥

## 四、技术方向 B：故障诊断引擎 + 边缘盒

### 4.1 数据链路（盒子只是关口，大脑在云/本地）

```
现场设备（伺服/PLC/机器人）
    ↓ EtherCAT / Modbus TCP / OPC UA（现有的通讯线，不新增接线）
[边缘盒 RK3588，约900元]
    ├─ 采集：周期读伺服状态字 0x6041、故障码 0x603F、PLC 报警区
    ├─ 脱敏：去掉客户工艺参数，只留故障特征
    ├─ 缓存断网续传
    └─ 上行：MQTT → 云端（或局域网直连本地 Agent）
    ↓
[诊断 Agent]
    ├─ 第一步：故障码精确匹配（汇川手册 RAG）→ 给出原因/处理步骤
    ├─ 第二步：匹配不上 → 结合上下文（当时状态、前后 5 秒变量轨迹）LLM 推理
    └─ 第三步：给出处置建议 + 关联历史案例（数据飞轮）
```

### 4.2 技术组件

| 组件 | 选型 | 说明 |
|------|------|------|
| 盒子硬件 | RK3588 工控盒（8GB，约¥900） | 只做采集/脱敏/缓存，不跑大模型 |
| 盒子软件 | Python 3.11 + asyncio | asyncua（OPC UA）、pymodbus、python-opcda 采集 |
| 通讯 | 主 EtherCAT CoE 读寄存器，辅 Modbus TCP / OPC UA | 0x6041/0x603F 通过 PLC 总线读，不加线 |
| RAG 知识库 | ChromaDB（本地）+ bge-m3 嵌入 | 汇川 AM400/AC900/SV660 手册 PDF 切片入库 |
| PDF 解析 | PyMuPDF | 手册转结构化文本 |
| 诊断 Agent | LangGraph + DeepSeek API | 先匹配后推理的两级诊断 |
| 诊断原型参照 | github.com/adityamhaske/plc-log-explainer-local | FastAPI+ChromaDB+Ollama 全本地 RAG，架构直接抄，手册换汇川的 |
| 第二阶段 | Neo4j 知识图谱（参考 tracefault 项目） | 设备-部件-故障因果图谱，处理复杂多因故障 |

### 4.3 你需要懂的最小知识（老王补课区）

- **EtherCAT**：现在非标设备主流的总线（就是设备里那根网线一样的黄线），伺服故障码沿这根线就能读到，不用额外接线
- **OPC UA**：工厂设备统一数据接口标准，是"工业设备的 HTTP"，IT 世界和设备世界之间的翻译官
- **0x6041/0x603F**：伺服驱动器标准寄存器（CiA402 协议规定），状态字和故障码，所有 EtherCAT 伺服通用——包括汇川 SV660

## 五、技术方向 C：InoProShop 适配验证（合伙人实测清单）

目的：确认汇川落地路径哪条通。**让合伙人装好 InoProShop + 拿一个旧项目，半天测完这 5 项：**

| # | 测试项 | 怎么测 | 判定 |
|---|--------|--------|------|
| 1 | PLCopen XML 导入 | 用标准 CODESYS 建小工程导出 XML → InoProShop 导入 | 导入成功且可编译 = XML 路线通 ✅ |
| 2 | 脚本引擎是否存在 | InoProShop 菜单找 Tools→Scripting；或看安装目录有无 CODESYS 脚本 DLL | 有 = 可走 MCP 直控（最优） |
| 3 | ST→梯形图互转 | 写一段 ST → 尝试切换到梯形图视图 | 能转 = 生成的 ST 电气工程师能接手维护 |
| 4 | 编译错误导出 | 故意写错一行 → 编译 → 看"消息"能否复制/导出成文本 | 能 = 错误可以回传给 AI 自动修复 |
| 5 | 软PLC 有无 | 看工程能否下载到 InoGDT/仿真器（汇川是否有自己的仿真） | 有 = 汇川生态内可做验证闭环；无 = 验证仍用标准 CODESYS 仿真 |

**结果影响：** 若 #1 通过，编程引擎输出格式定为 PLCopen XML，汇川路线成立；若 #2 通过则更好（可直控）。两项都不通，编程引擎第一阶段只服务标准 CODESYS 客户（WAGO/倍福/施耐德等，市场反而更大），汇川后续再攻。

## 六、集成架构：Agent 编排层设计（Codex 重点看）

### 6.1 分层

```
L1 交互层：桌面应用 UI（Tauri/Electron 壳 + Web 前端）
L2 Agent 编排层：LangGraph 状态机，意图路由 → 引擎分发 → 结果汇总
L3 工具层：MCP Client，统一调用：
    - codesys-tools（IDE 操控：建POU/写ST/编译/仿真/读写变量）
    - diag-tools（寄存器读取/RAG检索/案例检索）
    - io-tools（Excel IO表解析/PLCopen XML 生成）
L4 知识层：ChromaDB 向量库（手册/案例/模板）+ SQLite（用户/项目/日志）
L5 模型层：DeepSeek API（OpenAI 兼容），可配置切换本地 Ollama
```

### 6.2 一次典型调用（编程任务）

用户在 UI 输入工艺描述 + 上传 IO 表 → 编排层识别为编程意图 → 调 io-tools 解析 IO 表 → 调 L5 生成 ST → 调 codesys-tools 编译 → 报错 → 编排层组装"代码+错误"再调 L5 → 循环至通过 → 调 codesys-tools 下载软PLC跑测试 → 全绿 → io-tools 生成 PLCopen XML → UI 展示报告。**整个循环用户只按一次按钮。**

## 八、商业模式与合规底线

| 模式 | 内容 | 定价参考 |
|------|------|----------|

## 九、风险与对策

| 风险 | 概率 | 对策 |
|------|------|------|
